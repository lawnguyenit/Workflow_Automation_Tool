# Release 0.10.0 — Durable lead follow-up suppression gate

## Added

- `lead.followup_gate` with `check` and `record_event` operations, bound as `portfolio.lead_followup_gate`.
- PostgreSQL migration `005-lead-followup-suppression.sql` stores hashed event/subject identities and state transitions without raw contact/source identifiers.
- Explicit enrollment, idempotent reply/booking/opt-out suppression, manual pause, and manual resume bound to the exact pause event.
- Advisory transaction locks serialize duplicate source-event identities and per-subject transitions across workers. Database/configuration uncertainty fails closed.
- Database connection, lock-wait, and statement timeouts bound how long a blocked API execution can wait for PostgreSQL.
- Strict unit tests and a synthetic Compose/PostgreSQL integration harness cover retry, conflict, pause/resume, terminal stops, and concurrency.

## Guarantees and limits

- `DRY_RUN`/`REPLAY` never authorize sending. Unknown, paused, terminal, or unavailable state blocks follow-up.
- A stable, high-entropy `FOLLOWUP_IDENTITY_HMAC_KEY` (at least 32 bytes) is required for MOCK/REAL. No rotation/recovery tool exists; protect a backup and do not resume enrollment/sending after key loss until stop states are reconciled. Compose exposes the secret to API container operators. HMAC identifiers are pseudonymous, not anonymous; database access and retention still need protection.
- The module does not send or schedule messages, cancel an in-flight provider request, discover reply/booking/opt-out events, or define consent/message policy.
- It is not yet composed into the lead graph or an n8n workflow. No live service account or prospect data was used.
- `check` and an external network send are not one atomic transaction. The caller must check immediately before each send and use an appropriate outbox/provider policy.
